iOS app audit checklist for an existing Swift app

Before estimating new features, establish which code is live, whether the team can build it and what could block the next release. This checklist works for SwiftUI, UIKit and projects that use both.

12 November 2026By Oleg Yakushin

Match the released app to a buildable checkout

Record the version and build number in App Store Connect and identify the corresponding commit or tag. Then try a clean checkout using the documented Xcode version, package dependencies, scheme and configuration. Build it, run it on a physical iPhone and record the archive result separately.

Write down the steps a second developer would need to reproduce the build. If you can run the app in a simulator but an extension or signing configuration blocks a device build, list that issue before scheduling feature work.

Confirm who can ship the next update

List the owners of the repository, App Store Connect record, signing configuration, backend and integrations. Verify the access needed to install a beta, upload a build and submit the release. Record which tasks require the Account Holder or an administrator. Apple explains the roles in App Store Connect.

If the app is moving to another Apple Developer account, review Apple’s app transfer requirements before promising a date. List any app capabilities, subscription settings and services that will need work during the transfer.

Test the flows that can block a release

Choose two or three user journeys based on what the app does. Include the device and iOS version, whether it is a clean install or an upgrade, the steps and the result. Start with recent crash reports and support tickets to decide where to look. Apple’s guide to crash reports describes the available diagnostics.

  • Offline data. Upgrade from a previous build using test data, reopen the app offline and verify the records are still there. For a travel tracker such as DAY’S, stored trips and date calculations are central to the product.
  • Subscriptions. Use a test account to complete a purchase and restore access on a clean install. Record whether the build uses Apple’s sandbox, a local StoreKit configuration or another test setup. See Apple’s sandbox testing guide.
  • Hardware and extensions. Repeat the most important flow when the connection drops, permission is denied or the app goes to the background. In a hardware companion such as DetecFit, setup and reconnection belong in the release checks.

Turn the findings into a release plan

For each issue, write down the affected flow, the evidence, the smallest change that resolves it and the check that will close it. Prioritise anything that prevents a build or risks user data. Then address reproducible defects in the main flow and schedule the remaining changes around the next feature.

Example finding

A user with saved trips opens the updated build and sees an empty history. The release should wait until a test upgrade retains those trips and the country totals match before and after the upgrade.
